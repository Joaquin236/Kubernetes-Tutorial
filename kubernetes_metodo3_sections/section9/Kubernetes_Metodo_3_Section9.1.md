## 82.1º El sistema de red se basa en las tablas de enrutamiento, puerta de enlace, la dirección del host, dirección de los contenedores y las subredes del switch/router. El DNS identifica un nombre con las direcciones de cada servidor para escribir el nombre canónico y evitar adivinar/memorizar la IP del recurso asociado. Los espacios de nombre y el docker también forman parte de la infraestructura. 

## 82.2º El conmutador enlaza los servidores con los clientes para crear una red de conexión manual, si un servidor tiene la opción de distribuir direcciones IP, ofrecerá las direcciones IP a cada dispositivo conectado. El conmutador solo puede transmitir a una sola red por defecto, si se admite puede crear redes virtuales y/o dividir en más de dos subrredes.

## 82.3º El comando para añadir una dirección IP es:
ip addr add ["Dirección_IP/CIDR"] dev eth0

## 82.4º Si necesitamos interactuar con otra red diferente que tiene una Dirección o CIDR, no es posible usar una conexión directa, necesitamos una tabla de enrutamiento ofrecita por el router. El router recoge las direcciones de una infraestructura y con la puerta de enlace distribuye los metadatos a cada red, permitiendo que un dispositivo cliente/servidor o cliente/cliente ubicado en distintas red/subred se comunique sin errores.

## 82.4º El comanto para visualizar la tabla de enrutamiento es:

route add [Network_dir/CIDR] via [IP_Router/Gateway]

## 82.5º Si necesitamos que el host con Linux realice un avance de IP, tenemos que localizar el fichero ip_forward:
cat /proc/sys/net/ipv4/ip_forward
0
## Si usamos comando echo, 1 y la redirección de salida, se podrá cambiar el valor y permitir la transmisión de metadatos a través del sistema:
echo 1 > /proc/sys/net/ipv4/ip_forward
1

## 83.5º El sistema de red de Linux también usa los espacios de nombres para los contenedores. Los contenedores cuando están aislados no interpretan los procesos del contenedor adyacente. El comando [ps_aux] desde el contendor solo muestra un proceso. Mientras el mismo comando desde el host muestra todos los procesos. 

## 83.6º El host de la red tiene su interfaz conectada a la subred, las tablas de enrutamiento muentran las subredes a las puede alcanzar, las tablas ARP contienen información de la red local inicial. El contenedor dispone de una interfaz virtual con las mismas funciones que la interfaz del host.

## 83.7º Para crear un espacio de nombre nuevo usamos:
ip netns add [ns_name1] ; ip netns add [ns_name2]
## Para consultar los espacios de nombres:
ip netns
ip netns exec [ns_name(1-2)] ip link
ip -n [ns_name(1-2)] link

## 83.8º Para consultar las tablas ARP usamos
arp
ip nets exec [ns_name(1-2)] arp
ip nets exec [ns_name(1-2)] route

## 83.9º Para crear la conexión con el espacio de nombre, necesitamos un comando para establecerlo, conectando las interfaces virtuales a un cable virtual o tubería virtual:
ip link add veth-[ns_name1] type veth peer name veth-[ns_name2]
## Después de crear en enlace, necesitamos otro comando para añadirlo a los contenedores
ip link set veth-[ns_name1] netns [ns_name1]
ip link set veth-[ns_name2] netns [ns_name2]
## Este enlace aún no tiene las direcciones IP, el comando ip -n establece las IP
ip -n addr add 192.168.15.1 dev veth-[ns_name1]
ip -n addr add 192.168.15.2 dev veth-[ns_name2]
## La interfaz está desactivada por defecto, debemos activarla
ip -n [ns_name1] link set veth-[ns_name1] up
ip -n [ns_name2] link set veth-[ns_name2] up
## Para consultar la conexión, disponemos de los comandos
ip netns exec [ns_name1] ping 192.168.15.2
ip netns exec [ns_name2] ping 192.168.15.1

## También dispone de su propia tabla ARP
ip netns exec [ns_name1] arp
ip netns exec [ns_name2] arp

## 83.9º Existen complementos para crear redes virtuales más amplias con más de tres espacios de nombres. Open switch y Linux Bridge ofrecen estas oportunidades de crear una red interna virtual mayor
ip link add v-net-0 type bridge
## Para el sistema anfitrión es una interfaz más dentro del dispositivo servidor
ip link set dev v-eth-0 up
## Para enlazar la interfaz virtual con el puente, este proceso se realiza con todas las ns realizadas
ip link add veth-[ns_name(1-2)] type veth peer name veth-[ns_name(1-2)]-br
ip link set veth-[ns_name(1-2)] netns [ns_name(1-2)]
ip link set veth-[ns_name(1-2)]-br master v-net-0
ip -n [ns_name1] addr add 192.168.15.1 dev veth-[ns_name1]
ip -n [ns_name2] addr add 192.168.15.2 dev veth-[ns_name2]
ip -n [ns_name(1-2)] link set veth-[ns_name(1-2)] up
## Después de este paso, la transmisión aún sigue incompleta, necesitamos añadir una IP al v-net-0
ip addr add 192.168.15.5/24 dev v-net-0
## El comando ping debe transmitir los metadatos a nivel local. Esta conexión sigue siendo privada y no tiene enlace con el exterior de la red. La conexión con el exterior está en el puerto RJ-45 del sistema anfitrión. Esto se debe a que falta la ruta que enlaza el puente virtual con la red externa
ip netns exec [ns_name(1-2)] route
ip netns exec [ns_name(1-2)] ip route add 192.168.1.0/24 via 192.168.15.5
iptables -t nat -A POSTROUTING -s 192.168.15.0/24 -j MASQUERADE
## Al crear la tabla manual la red virtual debe conectar con la red local pero la salida a INTERNET sigue sin conectar. Necesitamos una ruta a todas las direcciones para lograrlo
ip netns exec [ns_name(1-2)] ip route add default via 192.168.15.5
## Aunque esté todo conectado desde el punto de vista de los servidores virtuales. El camino inverso que empieza desde el cliente no está configurado. Una de las opciones es: Reenviar los paquetes al puerto
iptables -t nat -A PREROUTING --dport 80 --to-destination 192.168.15.2:80 -j DNAT
